# fsmjs inspector

Look at a state machine.

[**Open the inspector**](https://evgkch.github.io/fsmjs/inspector/) · [по-русски](README.ru.md)

A machine's graph is a projection of the machine itself: `JSON.stringify` keeps the labels and
writes the name of every operation in place of its code. What is left is enough to draw the
machine, to check it — and, with no operations in it at all, to still run it. This tool is that
sentence made usable.

## The figure

A rule is a point `(from, on, to, emit)` — four discrete coordinates, and no drawing has four
axes. What it has instead is three blocks around two shared indices:

```
            ┌─────────────┐
            │  TO × EMIT  │  3 — the columns are shared down this line
   ┌────────┼─────────────┤
   │FROM×ON │  FROM × TO  │  1 and 2 — the rows are shared across this one
   └────────┴─────────────┘
```

**1** is the domain of δ: a row is a state, a column an event type, and one cell is one `(q, σ)` —
the pair a `dispatch` is addressed by. **3** is the codomain, `(r, λ)`. A rule that emits nothing
has no cell there, since there is no output to give it one, so the name of its column is what
names it. **2** is the same relation projected along Σ and Λ, so its cells are *sets* of rules:
several events may join one pair of states.

1 and 3 are the two halves of a transition — the library's own words for them are the **cause**
(`source` and `input`) and the **effect** (`target` and `output`) — and neither is more its
beginning than the other. Point at a cell of either and its two bands run out to the names on both
axes, the one 2 has an axis for carrying on across it, and what the other half could be lights up.
Press to fix that half; press the other and the rule is taken. 2 is a display and never a control:
point at a corner and it lights every `ON` the rules there go out on and every `EMIT` they arrive
with. A crossing is not something to choose.

What is drawn beyond the schema is what the schema does not say in any one place: which states no
run reaches, which have nothing leaving them, which pairs are connected but not by one rule, and
which rules `validate` finds can never fire. There is no second view and no third: `toRules`,
`toTree`, `toDot` and `formatIssues` all write the schema again in other words, and the schema is
already open on the left. The figure earns its place by saying what none of them can — where the
machine stands, what it can do from there, and what it has done.

## Two ways to work it

Off the **explore** flag, a machine stands somewhere: `FROM` is where it is and moves with it,
everything out of its reach is dim and does not even answer the pointer, and naming both halves of
a transition takes it. On, no state is current, the whole schema is on the table, and nothing
fires — there is nothing standing anywhere to move.

## What it reads

A schema, as JSON — paste it, or pick one of the bundled ones. Six come with it, and three of
those are not written by hand: they are `JSON.stringify` of the machines this tool itself runs on,
regenerated by `npm run dump` before every build. Open *the inspector's choice* and the figure
draws the thing that was deciding what the figure did while you were pointing at it.

A guard read back from JSON is a name and not code, so a dump has lost the one thing that tells
two rules of the same cell apart. The tool hands it back: every rule is built with a guard that
asks whether it is the rule you named, so your second press *is* the guard. `with` still reads as
the identity, so the context stays as it started — the machine being driven is a real one
throughout, and that is the point.

## A machine that is running

The inspector is an application you run, and what an application being debugged writes is one word.

```sh
npm install
npm run inspect      # the inspector, and the relay it listens on
```

Then, in the application being debugged — as many machines as it has:

```ts
import { inspect } from "@evgkch/fsmjs-inspector";

const cart = inspect(new StateMachine(schema, start), { name: "cart" });
inspect(upload, { name: "upload", description: "retries, and when it gives up" });
```

`inspect` hands the machine back. It is the identity function with a listener attached, so it goes
around an instance that already exists and comes off by deleting one word.

Rewinding the run from the inspector's own window is turned on by handing over a recorder you
already have:

```ts
import { history } from "@evgkch/fsmjs/debug";

const past = history(cart);
inspect(cart, { name: "cart", history: past });
```

The instance is the permission and the fact at once. A flag would have meant the inspector calling
`history(cart)` on your behalf, and then the line that switches the debugger off is also the line
that takes away a recorder your undo may have been using — and an application that already records
would record twice. Hand over what you built, and deleting the call leaves everything you built
exactly where it was.

Every machine announces itself, so what is along the top of the inspector is a roster of who is out
there and you pick; `?ws=ws://host:port` points it at a relay on another host. The entry point an
application imports has no document in it and loads no stylesheet — what is being watched may have
no DOM at all, and a server should not be importing a page to say what a machine did.

One copy of `@evgkch/fsmjs` in the application, and it is the only hard requirement: the library is
a peer dependency and stays out of the bundle, because a second copy is a second `TRANSITION`
symbol and the listener would never fire.

The figure can also be put on the page being debugged, rather than in a window of its own —
`overlay(fsm)` from `@evgkch/fsmjs-inspector/ui`, with `@evgkch/fsmjs-inspector/style.css`. It
takes the same recorder in the same way (`overlay(cart, { history: past })`), and it is the right
half only when the page you want the figure on is the page you are debugging: it draws, so it
costs a stylesheet.

What crosses the wire is names: the schema as `JSON.stringify` writes it, and the four types of
every transition. No context, no payload — an application's data does not leave it, and a context
that could never be serialized is not a problem.

What a remote subject can do is what the application handed over, and nothing else: no `drive`,
because sending an event into another process is a right this hop has not been given, and no
`rewind` unless a `History` came with it. That is the whole of read-only — not a mode, an absence,
and every part of the tool already asks.

## Running it

```sh
npm install
npm run dev
```

`npm run build` writes a static site to `dist/`: `npm run dump` refreshes the schemas the tool
keeps of itself, `tsc --noEmit` is the gate, and `vite build` does the rest. `npm run build:lib`
writes the package into `dist-lib/` — the one word an application writes, the tool that draws, and
the stylesheet.

## Layout

```
index.html     the standalone page
viewer.html    the page that watches machines running elsewhere
src/           the tool
schemas/       what it can be pointed at, its own machines included
scripts/       dump.mjs writes three of those · relay.mjs carries the wire
```

Inside `src/`, the layers run one way: `shared` → `entities` → `features` → `widgets` → `pages` →
`app`. The seam the whole thing turns on is `entities/machine`: a `Subject` is what a figure needs
about a machine and the whole of it, and there are three — a dump in an editor, a machine in this
scope, and a machine at the end of a pipe. Everything remembered is a machine of the library's own:
what is held and where the pointer is, what the mode is, what the editor is doing to a word, how
the page is arranged, which machine out there is on screen. All of them are the library, running
the tool that explains it.
